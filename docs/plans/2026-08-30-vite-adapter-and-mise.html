Devtree design plan · Started August 30, 2026 · Revised September 5, 2026 · Proposed

Set up a session once.
Use it from your shell and dev server.

Devtree should give a checkout a consistent development environment before its server starts. It should also work without a Vite plugin or a generated .env file.

This plan makes sessions persistent, moves Vite configuration into the command that launches it, lets mise bring the session’s environment into your shell, and adds guided setup for new and existing projects.

What this feels like to use

You enter a worktree. The mise plugin calls the checkout’s devtree env --json. Devtree finds the checkout’s session, or creates one that has not started yet, and returns its environment variables.

Your shell now knows the session’s URLs and dependency settings. When you run devtree dev, Devtree starts that same session with the same port assignments. When you stop it, the session stays around for next time.

A session can exist without a running server. Its name, dependency owner, and assigned ports survive stopping and restarting development.

Mise is optional. Projects can keep using package scripts and .env files. Everyone benefits from removing the Devtree plugin from their Vite configuration.

Guide the developer from an empty configuration to a working session

After adding Devtree to a project, run:

pnpm devtree setup --interactive

The guide works even when no Devtree configuration exists. It detects what the project already uses, recommends matching defaults, and asks only the questions needed for the chosen setup. A developer should not need to read this plan to get started.

  1. Understand the project. Detect the package manager, Vite or VitePlus, existing Devtree configuration, mise tasks, env provider, and dependency definitions. Show what was found and let the developer correct it.
  2. Choose how to run development. Offer package scripts or mise. For mise, select an existing server task or create one, enable shell environment loading, and install the bundled adapter in its stable location.
  3. Choose how to reach the application. Explain local and Tailscale access in terms of who can open the URL. Collect the routing provider and hostname settings needed for that choice. Show a preview of the resulting URL. Reuse the existing Caddy and Tailscale setup for its branch of the guide.
  4. Choose environment and dependencies. Preserve an existing env provider by default. For a new mise setup, recommend process; otherwise recommend dotenv. Offer Varlock when wanted. Let the developer configure required managed values, select an existing dependency stack, define supported dependencies, or proceed without dependencies. Explain which commands and migrations will run; do not invent application-specific settings.
  5. Review and apply. Show the files to create or edit, plugin registration, dependency installations, and any machine-level routing changes. Let the developer go back and adjust choices, then apply the reviewed setup. Preserve unrelated configuration and scripts.
  6. Verify and finish. Run the relevant doctor checks, create or reuse the session, and offer to start dependencies and run configured setup hooks. Help resolve missing tools, authentication, DNS, or certificate setup. Offer to start the dev server; if accepted, verify that its public URL responds. Otherwise leave the session ready to start and print the exact command.

End with a short result: the selected session, its URL, what changed, and any remaining action. Distinguish “configuration saved” from “application verified.” If an external step must happen first, save completed progress and explain how to resume.

Rerunning the guide edits the existing setup with current values preselected. Cancelling before apply changes nothing; cancelling after apply reports what was completed. Keep plain devtree setup noninteractive for scripts and automation. devtree dev -i remains the session picker.

Setup intentionally creates project configuration. The promise of no generated checkout files applies to normal operation with the process provider, not to this explicit configuration step.

Give sessions a life beyond the process

Today the session registry tracks running processes. When the controller process dies, its record is removed. We will keep the session and track whether it is stopped, starting, or running.

ActionResult
devtree envFind or create the session, then print its environment. Start no processes.
devtree devStart the existing session, creating it first if needed.
Stop the serverMark the session stopped. Keep its identity and port assignments.
Remove the sessionDelete its saved state and release its assignments. The command syntax still needs to be chosen.

Both commands use the checkout’s selected session. If there is no selection, they use today’s defaults. Selecting a named session persists that choice, so later shell exports and startup agree. A running session’s identity or dependency selection must not change silently.

Session state lives under ~/.devtree. So devtree env may write Devtree state, but it writes no files in the checkout. The existing limit of one live session per checkout stays.

What happens to ports?

Devtree already calculates ports from the project, session, and endpoint names. This also works with Caddy; the old plan’s claim that Caddy needs a separate reservation mechanism was incorrect.

Use that calculation to choose an initial port, check assignments held by other Devtree sessions, and save the chosen port with the session. Startup then reuses it. Concurrent session creation must not assign the same managed port twice.

This reserves the assignment within Devtree. Another application can still occupy the port. In that case, startup reports the conflict instead of silently switching ports and disagreeing with the shell.

Remove the Vite plugin

Devtree already starts Vite with flags for the listening address, port, and screen clearing. It can also pass the allowed public hostname through Vite’s environment variable. That makes the Devtree Vite plugin unnecessary.

Consumers remove their devtree/vite import and plugin call. Devtree prints the session name, public URL, and instance ID before starting the server. New projects do not need a Devtree-specific change to vite.config.ts.

Each session has one public hostname: local or Tailscale. We are not adding simultaneous support for both.

This is a breaking change. Existing plugin imports will fail until removed. Varlock users must also add the standard Varlock Vite plugin themselves; Devtree will continue launching their commands through varlock run.

Choose how the environment reaches your tools

Keep the existing providers and add process:

ProviderBehavior
dotenvKeep managing the checkout’s env file. Proposed default, as today.
varlockKeep the existing env-file behavior and Varlock command wrapper.
processPass managed values to the server, hooks, and dependency commands without creating or changing an env file.

Separately, remove the dotenv package dependency. Node 24 already provides an env parser. The provider name can stay; file support does not require that package.

Export the session’s values

devtree env          # KEY=value lines for inspection
devtree env --shell  # Shell-quoted export statements
devtree env --json   # A JSON object for scripts

All forms resolve the same session and values as devtree dev. Keep the existing env write and env show commands working, and share session resolution with devtree exec.

Let mise load them into the shell

Ship a small mise environment plugin inside the Devtree npm package. The plugin asks the checkout’s Devtree CLI for JSON and passes the returned values directly to mise. No helper shell script or eval is needed.

After installing the project’s dependencies, the developer registers the bundled plugin once. Proposed command:

pnpm devtree mise install

This copies the adapter into ~/.devtree/mise/devtree and registers that stable directory with mise. It does not link into node_modules or a worktree that might later be deleted. Rerunning the command updates the installed adapter.

A project using provider: "process" then enables it in mise.toml:

[env]
_.devtree = { tools = true }

[tasks.dev]
run = "devtree dev"

The adapter is installed once per user. Each checkout still uses its own Devtree package version, configuration, and selected session. Session logic stays in the CLI; the shared adapter only requests and translates its output.

Start with uncached plugin output so session changes are reflected at the next mise environment refresh. Caching can come later with explicit watches for session selection and configuration changes.

Let mise run the server too, if useful

Devtree can already call mise tasks from hooks. Add a runner option so a mise task can also launch the dev server:

// devtree.config.ts — dev_server section
dev_server: {
  runner: { kind: "mise", task: "vite:serve" },
}
# mise.toml
[tasks."vite:serve"]
run = "vite dev"

Devtree supplies the Vite flags and session environment. Mise supplies the task and tools. This plan supports Vite, VitePlus, and mise tasks that accept Vite flags; other server types are outside its scope.

Deliver it in four pull requests

  1. Remove the Vite plugin. Pass the hostname in the server environment, move the startup messages into Devtree, and remove the plugin export and peer dependencies. Update examples and migration instructions in the same change. Verify real requests against Vite and VitePlus.
  2. Persist sessions and export their environment. Extend the registry and shared session resolver, retain assignments after stopping, add the export formats and process provider, and replace dotenv’s parser. Include migration of existing records and explicit session removal.
  3. Add mise integration. Bundle the environment plugin, add its installation command and the task runner, and provide a complete example. Check installation, updates, use across worktrees, argument forwarding, Varlock wrapping, and environment refresh.
  4. Complete the guided setup. Expand setup --interactive beyond its current Tailscale flow. Support projects without configuration, detect existing choices, review and apply changes, install the mise adapter when selected, and verify the first session. Document reruns and recovery from interrupted setup.

The second pull request carries most of the design work. Before implementing it, settle the saved record format and session removal command. Keeping dotenv as the default remains a proposal; persistent sessions, removing the dotenv package, and bundling the mise plugin with installation under ~/.devtree are agreed decisions. Full interactive guided setup is also in scope.

Details for implementation and review

The behavior above is the plan. These notes capture the contracts and checks needed to implement it.

Guided setup implementation and acceptance checks

Extend src/interactive-setup.ts and the existing @clack/prompts interface. Today this flow requires loaded configuration and concentrates on Caddy/Tailscale. Dispatch guided setup before mandatory configuration loading so a new project can use it.

Reuse configuration writers, doctor checks, session resolution, dependency operations, and mise installation. Generate the minimum configuration for the selected choices. Keep project settings separate from machine-specific overrides. Merge supported structured files; for existing executable TypeScript configuration, avoid destructive rewrites and present precise edits when they cannot be safely automated.

Detect missing tools early. Offer supported installation commands as part of the reviewed actions, and give concrete instructions for steps requiring the developer’s login or external administration. Never claim those steps succeeded without checking. Existing projects with the removed Vite plugin also need migration guidance, including Varlock integration where relevant.

Do not ask every developer every possible question. Use existing values and detected defaults, reveal advanced options only when needed, and provide a way to go back before applying. In a noninteractive terminal, an explicit request for the guide should explain how to run it interactively.

Verify: a fresh Vite project completes local setup; a mise project gets the adapter and correct shell values; an existing configuration retains unrelated settings; Tailscale setup can pause for DNS and resume; cancellation before apply writes nothing; repeated setup does not duplicate scripts or settings; partial failures report completed work; dependency reuse respects ownership; the finish screen accurately distinguishes saved, ready, and running states.

Session storage and lifecycle

Start with src/environment-registry.ts, src/session-options.ts, and src/instance.ts. Separate saved identity and endpoint assignments from controller and runner process IDs. Repeated env exports must reuse a session safely.

Migrate existing live records. A dead controller or failed startup leaves a stopped session; it does not delete the identity. Review registry consumers so stopped sessions do not count as live dependency users or retain active routes. Preserve checks against duplicate live sessions.

Explicit removal releases assignments and must not discard a running session without stopping it. Persisted assignments must be used when computing both exported values and server startup settings.

Verify: create through env export, export again, start, stop, restart, crash cleanup, named selection, concurrent creation, occupied ports, removal, and migration. Check that stopped sessions do not block valid startup or dependency operations.

Vite’s launch contract 
vite dev --host 127.0.0.1 --clearScreen false --port N --strictPort

Set __VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS to the one active public hostname in the dev server’s child environment. Keep this Vite-specific value out of shell exports and unrelated commands.

Remove src/vite.ts, the ./vite package export, and peer dependencies on Vite, VitePlus, and the Varlock Vite integration. Keep Vite and VitePlus as development dependencies for validation.

Verify: start each real server with an allowed hostname. A request using that Host header must succeed; an unrelated hostname must be rejected. This is the compatibility check for the environment-variable contract when upgrading Vite.

Vite may still print its loopback URL. Devtree’s printed public URL is the one developers should open. Running Vite directly bypasses Devtree and no longer produces the old plugin warning.

Environment output and parser compatibility

Share computation across dev, env, and exec. Exports include the managed entries and DEVTREE_* metadata, but not the parent process’s entire environment or Vite’s private setting. Accept the same session and dependency selection flags as dev.

Keep shell and JSON output free of startup messages. Shell quoting must handle spaces, quotes, and newlines. The process provider must skip env-file writes for all relevant command paths.

Replace the two dotenv parsing calls in src/env-file.ts with parseEnv from node:util, then remove the package dependency.

Verify: exported values match those supplied at startup; shell output survives sourcing; process mode leaves checkout files untouched; dotenv and Varlock still work. Check parser compatibility with representative quotes, escapes, comments, and multiline values.

Mise plugin installation and environment loading

Include the Lua plugin metadata and hooks/mise_env.lua in the published npm package. The proposed devtree mise install command copies these files to ~/.devtree/mise/devtree, then uses mise plugins link to register that directory. Keep setup explicit rather than running it from an npm installation hook.

Mise registers plugins globally by name. Repeated installation should reuse or update Devtree’s stable adapter directory. If the name already points to an unrelated plugin, report the conflict rather than silently replacing it. Keep the adapter’s JSON contract small and compatible across supported Devtree versions.

Resolve the CLI from the current project’s installed Devtree package, including when invoked from a subdirectory. Do not fall back to another checkout or a global Devtree executable. If dependencies are missing, explain how to install them. Invoke the CLI directly without recursively running mise exec or a mise task.

The hook parses devtree env --json and returns mise’s key/value entries. Use tools = true so the project’s Node runtime is available. Disable plugin-output caching initially. Measure export cold-start time through tsx; target under 300 ms. Any later caching must account for the selected session, configuration inputs, and local CLI version.

Verify: the packed npm artifact contains the plugin; installation and updates work; deleting the installation checkout leaves the adapter intact; two worktrees use their own CLI versions and session values; missing dependencies produce a useful error; changing session selection refreshes the environment.

References: Mise plugin installation and environment plugin hooks.

Mise task arguments and Varlock

The new runner produces:

mise run vite:serve -- --host 127.0.0.1 --clearScreen false --port N --strictPort

Keep the existing Vite and VitePlus runner options. Apply Varlock wrapping outside the mise command when selected.

Varlock consumers configure their Vite integration directly:

import { defineConfig } from "vite";
import { varlockVitePlugin } from "@varlock/vite-integration";

export default defineConfig({
  plugins: [varlockVitePlugin({ ssrInjectMode: "init-only" })],
});

Verify: task arguments and environment reach the server, hooks can still run mise tasks, and Varlock wrapping remains intact. Exercise the example with a changed session selection to check shell refresh behavior.

Scope: session persistence, environment delivery, Vite launch configuration, optional mise integration, and guided project setup. Session naming rules, dependency sharing, and routing providers stay as they are.
